3. Containers (Docker)

  • api/Dockerfile: multi-stage. O 1º estágio instala as dependências num venv, e a imagem final python:3.12-slim leva só o venv e o código. Roda como usuário não root (uid 10001), com HEALTHCHECK em /health.
  • front/Dockerfile: front servido por nginx sem root, com proxy de /api para a API.
  • docker-compose.yml: sobe front + API + Postgres. A API só escuta em 127.0.0.1, e o acesso público passa pelo front. O profile monitoramento sobe Prometheus e Grafana.
  • Nenhum segredo dentro da imagem. Senhas e chaves vêm de variáveis de ambiente (.env local, fora do Git, ou App Settings na nuvem).
  • O Trivy varre as duas imagens no pipeline e barra qualquer CVE HIGH/CRITICAL com correção disponível. As imagens atuais passam sem nenhuma.

4. Infraestrutura como código (Terraform)

devops-cloud/terraform/ descreve o ambiente inteiro: resource group, App Service Plan F1 (Linux) e o Linux Web App Python 3.12.

Exigência de segurançaComo o Pátio Monitor atende
Expor só 80/443O App Service só recebe tráfego HTTP/HTTPS, e https_only = true redireciona o HTTP para HTTPS. TLS mínimo 1.2, HTTP/2 ligado.
Porta 22 nunca aberta para 0.0.0.0/0Não existe SSH público. O console Kudu/SCM só aceita login Entra ID com RBAC, porque a autenticação básica (usuário e senha) de SCM e FTP está desligada e o FTP/FTPS está Disabled.
Segredos fora do códigoO Terraform só grava configurações não secretas. INGEST_API_KEY, METRICS_TOKEN e ASSISTENTE_URL são gravadas pelo pipeline a partir do GitHub Secrets e ficam em ignore_changes, para não passarem pelo state.
.tfvars fora do repositórioO .gitignore bloqueia *.tfvars e *.tfstate. No repositório só existe o terraform.tfvars.example, sem valores reais.
StateO state é local e fica fora do Git. Um backend remoto num Storage Account consumiria crédito da assinatura, e a meta do projeto é custo zero. Para uma equipe maior, o próximo passo é o backend azurerm com lock.
Por que App Service e não uma VM. A VM exigiria abrir e manter portas, SO e patches, e custaria crédito (uma B1s fica ligada 24 h até 26/11). O App Service F1 é PaaS: a Azure cuida do SO e do runtime, o custo é US$ 0, e a superfície de ataque é menor, porque não há porta 22 para proteger. A mesma API roda em container no docker compose, o que demonstra a parte de containers.

Problemas reais encontrados no provisionamento

  • x509 / CERTIFICATE_VERIFY_FAILED: o "Web/Mail Shield" do antivírus Norton intercepta HTTPS com uma CA própria. O Azure CLI (Python) e o Terraform (Go) não confiam nela. O antivírus intercepta até o TLS local entre o Terraform e o plugin azurerm. A correção foi juntar a raiz do Norton ao cacert.pem do Azure CLI (REQUESTS_CA_BUNDLE) e rodar o Terraform com TF_DISABLE_PLUGIN_TLS=1, que desliga só esse TLS local entre os dois processos (a conexão com a Azure continua em HTTPS).
  • Recursos criados antes do Terraform funcionar: durante o bloqueio do certificado, o ambiente foi criado com az CLI. Depois, os 3 recursos foram trazidos para o código com terraform import e o terraform apply alinhou a configuração. Desde então o terraform plan não mostra diferença: a nuvem é gerida pelo Terraform.
  • Política de regiões do Azure for Students: só libera brazilsouth, chilecentral, canadacentral, eastus2 e centralus (RequestDisallowedByAzure em eastus).
  • Limite de 1 plano F1 Linux por região: o F1 de Brazil South estava ocupado por um projeto antigo, que foi removido para liberar a região.

6. Observabilidade (Prometheus + Grafana)

A API expõe /metrics no formato Prometheus (prometheus-fastapi-instrumentator). Na nuvem esse endpoint exige token: sem ele a resposta é 401. O Prometheus roda localmente pelo docker compose --profile monitoramento e lê o MVP publicado por HTTPS com Bearer (job patio-azure, a cada 30 s, para não gastar a cota de CPU do F1).

Sinal de ouroPainel no Grafana
LatênciaLatência p95 por endpoint (histogram_quantile sobre http_request_duration_seconds)
TráfegoRequisições por segundo
Erros% de respostas 4xx/5xx
SaturaçãoCPU e memória do processo da API

Alertas (alertas.yml):

  • LatenciaP95PosicoesAlta: p95 de /posicoes acima de 300 ms por 2 min. É assim que a promessa de baixa latência do produto é medida, em vez de ser só afirmada.
  • TaxaDeErros5xx: mais de 5% de respostas 5xx.
  • ApiFora: alvo sem responder por 1 min.

O que foi medido

  • Latência: com cerca de 800 requisições reais em 5 minutos (13/11/2026, 21h), o p95 de /api/posicoes e dos demais endpoints ficou em ~95 ms, abaixo da meta de 300 ms do alerta.
  • Alerta disparado (teste controlado de queda): às 21:24 o App Service foi parado de propósito (az webapp stop). O up do job patio-azure foi a 0, o alerta ApiFora passou de pending para firing, e às 21:30 o app foi religado (/health voltou com 200). O painel "Alertas do Prometheus" do dashboard mostra o disparo.

8. Dados pessoais (LGPD): onde ficam

O único dado pessoal do domínio é o do motorista (matrícula e nome). No projeto ele é fictício: é gerado pela portaria simulada com nomes do tipo "Motorista A".

LugarDado do motorista
Portaria simulada (pasta chegada/ do repositório patio-monitor-bigdata, fora do Git) e camadas Bronze/Prata no DatabricksTexto (fictício)
Camada Ouro (fato_permanencia) no DatabricksSó hash SHA-256 da matrícula e do nome
Export CSV da Ouro, API, SQLite do App Service, Postgres do composeNenhum: o export não tem as colunas, e a API ainda filtra qualquer coluna com "motorista"
Logs da API e do assistenteNenhum

Limite conhecido: SHA-256 sem sal de um nome pode ser revertido por dicionário. Com dados reais, o certo seria HMAC-SHA-256 com a chave num cofre (Azure Key Vault), e não um hash puro.

10. Conclusão

O Pátio Monitor está publicado numa URL pública em HTTPS, com custo zero, e só chega à nuvem por um pipeline que testa, procura segredos, faz análise estática e varre dependências e imagens antes do deploy. A execução barrada mostra o pipeline impedindo que um segredo vá para produção. O Grafana mede a latência que o produto promete, em vez de só afirmá-la.
